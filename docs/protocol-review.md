# Задача №8: проверяемая подготовка протокола

Состояние реализации: 30 сентября 2026 года. Новый режим реализован локально и
включается отдельно. Приёмка на реальных записях и окончательный шаблон ещё нужны.

## Что удалось установить по предоставленным материалам

Локально изучены 5 DOCX и 3 M4A. Их содержимое, имена участников и сами файлы
не включены в Git и не отправлялись во внешние сервисы при разработке.

- Четыре документа по структуре похожи на протоколы, один — на речь в прениях.
- У двух протоколов повторяются шапки: шесть и две соответственно. Это примеры
  дефекта; повторение не является правилом шаблона.
- В четырёх протоколах используется Times New Roman 12 pt, поля слева 3 см,
  справа 1,5 см, сверху и снизу 2 см. Эти параметры сохранены как предварительные.
- Длительности аудио: примерно 7,8, 20,2 и 21 минута. По именам файлов есть одна
  очевидная пара аудио/DOCX, но соответствие содержания ещё не проверено.
- Пользователь не знает, какие DOCX исправлены вручную. Ни один документ пока
  не принят за эталон допустимых изменений речи или обязательных фактов шапки.

## Включение и совместимость

`PROTOCOL_MODE=legacy` остаётся значением по умолчанию. Для тестовой установки
задайте `PROTOCOL_MODE=review` в окружении приложения и перезапустите его.
Режим записывается при создании задания. Существующие задания продолжают
обрабатываться своим конвейером, старые документы остаются доступны.

Новый промпт `prompts/review-protocol.md` входит в образ. Его точная копия,
хеш и версия сохраняются с анализом; повтор использует ту же копию.
Модели берутся из уже настроенных `LLM_MODEL` и `LLM_FALLBACK_MODELS`.
Новых провайдеров конвейер не добавляет.

Для отката новых загрузок достаточно вернуть `PROTOCOL_MODE=legacy`.
Для просмотра уже созданных проверяемых документов нужен код нового режима.
Удаление задач старой версией приложения также удалит новые артефакты:
эта операция закреплена триггером SQLite.

## Обработка и хранение

1. Ответ ASR нормализуется в последовательность реплик с постоянными ID,
   исходными speaker ID, неизменённым текстом, временем и доступной уверенностью.
   Исходник и его хеш сохраняются **до** первого обращения к модели.
2. Длинные реплики делятся на сегменты с абсолютными позициями; разбиение
   старается использовать границы предложений. Склейки с переписанным контекстом нет.
3. Модель возвращает JSON: обработанные сегменты, локальные замены, предложения
   ролей с цитатами и сомнительные места. Во все следующие части передаётся
   накопленный реестр предложений; противоречия сохраняются для проверки.
4. Код проверяет схему, полноту списка сегментов, ID, диапазоны Unicode-символов,
   точное совпадение исходника, отсутствие пересечений и наличие цитат-оснований.
   Пустые замены и вставки новых структурных строк запрещены.
5. Сохраняется каждая успешно проверенная часть, модель, токены и время запроса.
   Частичный/невалидный ответ не считается готовым результатом. Ограниченный
   повтор и явно настроенный fallback не могут заменить исходник черновиком.
6. Даже корректное предложение остаётся неприменённым до решения пользователя.
   Проверки диапазонов не доказывают сохранение смысла. Изменения чисел, отрицаний,
   предполагаемых имён и крупные сокращения дополнительно отмечаются в интерфейсе;
   отсутствие такой отметки не означает, что правка безопасна.
7. Экран и Word строятся из одинаковых блоков. Шапка создаётся один раз кодом.
   Пустые сведения опускаются; фамилии, даты, закрытие заседания и CD-R не
   подставляются из примеров. Сказанные перерывы и возобновления остаются в репликах.

`protocol_reviews` хранит исходник отдельно от небольшого состояния задания;
список задач и обычный polling его не загружают. Доступ к исходнику, правкам,
повтору и Word проверяется по владельцу. Сохранение использует номер ревизии:
изменения из устаревшей вкладки отвергаются, а её локальный текст остаётся на экране.

Срок хранения совпадает с заданием (`JOB_TTL_DAYS`, по последнему обновлению).
Удаление задания, аккаунта и автоматическая очистка удаляют исходник и правки
тем же SQLite-триггером. Они попадают в существующие резервные копии базы и
подчиняются срокам хранения этих копий. Нового серверного хранилища аудио нет.

## Работа пользователя

Открыть «Проверить» у нового протокола. Для каждой предложенной правки можно
выбрать «Принять», «Отклонить» или отложить решение. Рядом остаётся исходный текст.
Ручная редакция сохраняется отдельно и имеет приоритет над принятыми предложениями
для этой реплики; её можно отменить без потери исходника.

Роли подтверждаются для голосов; при ошибке диаризации доступно переопределение
для одной реплики. Неустановленная роль сохраняет метку спикера. Сведения для шапки
и подписей вводятся отдельно. Предположения модели никогда не заполняют их сами.

Исходную аудиозапись можно выбрать локально и прослушивать с времени реплики.
Этот выбор не отправляет файл на сервер. Если файл ещё есть в очереди текущей
вкладки, он подключается автоматически. После перезагрузки обычный загруженный
файл потребуется выбрать снова. Правила хранения записей встроенного диктофона
этим режимом не расширяются.

До явного подтверждения проверки Word содержит отметку «ЧЕРНОВИК». Подтверждение
требует завершённого анализа, решения по всем предложениям, проверки замечаний
и явного выбора ролей (включая «Роль не установлена»). Это отметка пользователя,
а не автоматическое доказательство точности документа.

После ошибки «Повторить анализ» использует сохранённый исходник и пропускает
готовые части; повторное распознавание и загрузка аудио не нужны. Одновременно
действуют обычный лимит активных задач и защита от повторного запуска.

## Проверки и следующий этап

Автоматические тесты используют только синтетические данные. Проверяются:
повторяющиеся слова, Unicode-позиции, длинные реплики, неверные ID, пересечения,
неполные JSON-ответы, отказы и fallback, восстановление, удаление во время анализа,
сроки хранения, чужой доступ, старые документы, конкурирующие сохранения,
соответствие Word экранным блокам, сохранение решений и безопасный вывод текста.

Для реальной приёмки ещё необходимо:

1. Прогнать согласованную аудиозапись через оба режима на тестовой установке.
2. Проверить по записи пропуски ASR, смысловые изменения и роли. Сравнить
   количество ручных исправлений, время, токены и фактическую стоимость.
3. Получить подтверждение оформления и правил редактирования хотя бы одного
   окончательного протокола. Текущий шаблон предварительный; нет отдельной
   структурной модели нескольких заседаний внутри одной записи.
4. Уточнить удобство ручной проверки на длинной записи и политику обязательных
   реквизитов. Уверенность ASR и модели не является критерием приёмки.
5. После приёмки решить, включать ли новый режим по умолчанию. Задача №8 пока
   не считается полностью закрытой.

Контракт провайдера проверен по [документации OpenRouter о structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs):
`response_format=json_schema`, `strict=true`, `provider.require_parameters=true`.
Клиентская валидация обязательна независимо от поддержки схемы провайдером.
